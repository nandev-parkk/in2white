# 로딩 표시 및 검색 전환 개선 설계

상태: 2026-09-22 사용자 승인 후 구현·검증. 기존 테스트 실패 4개는 구현 계획 결과에 별도로 기록했다. 분류: Bug / Standard.

## 목표

짧은 요청에서 로딩 문구와 스켈레톤이 번쩍이는 현상을 줄이고, 긴 최초 로딩은 기존 디자인 시스템을 이용해 정돈된 위치에 표시한다. 검색·정렬·페이지 변경은 이전 결과를 유지한다.

## 표시 계약

1. 최초 조회·지연 모듈 로딩의 표시 임계값은 300ms이다. 임계값 이전에는 시각적 로딩 표시와 라이브 안내를 노출하지 않는다.
2. 대기 중에도 페이지 셸, 이미 알려진 제목·툴바 및 콘텐츠 영역의 높이를 유지한다. 단순히 전체 레이아웃을 `null`로 바꾸지 않는다.
3. 300ms 이후 데이터가 없으면 스피너와 짧은 문구를 콘텐츠 영역의 수평·수직 중앙에 표시한다. 전체 화면과 목록 영역을 구분하며 모바일에서도 영역을 넘지 않는다.
4. 멤버 목록·사용자 선택기·프로젝트 상세 헤더 등 이미 스켈레톤을 사용하는 곳은 형태를 유지하고 최초 노출만 지연한다. 각 행이 아니라 그룹 단위로 지연한다.
5. 완료되면 즉시 실제 콘텐츠를 표시한다. 최소 노출 시간을 강제해 빠른 응답을 늦추지 않는다. 따라서 300ms 직후 완료되는 요청까지 짧은 노출을 완전히 없애는 설계는 아니다.
6. 화이트보드 데이터 조회와 lazy 편집기 준비는 동일한 화면 크기·정렬·로딩 표현을 사용한다. 가능한 한 연속 로딩 구간의 표시 상태를 유지해 중간 공백과 재점멸을 피한다.
7. 검색·정렬·페이지 변경과 배경 재조회에서는 이전 결과를 유지한다. 스켈레톤, 스피너, 흐리게 처리하는 오버레이로 기존 결과를 대체하지 않는다. 검색 입력은 계속 사용할 수 있다.
8. 새 결과의 빈 상태는 새 응답이 확정된 뒤 표시한다. 기존 페이지의 데이터와 새 페이지 번호를 혼합하지 않으며 기존 페이지 이동 버튼의 요청 중 비활성화 정책은 유지한다.

## Query 적용 및 권한·오류 계약

[TanStack Query 공식 문서](https://tanstack.com/query/latest/docs/framework/react/guides/paginated-queries)는 `placeholderData: keepPreviousData` 또는 `(previousData) => previousData`를 안내한다. query key가 바뀌어도 마지막 성공 데이터를 유지하며 `isPlaceholderData`로 이 상태를 구별한다.

- 대상은 프로젝트 목록, 화이트보드 문서 목록, 멤버 목록과 기존 멤버 후보 검색이다. 모든 GET 요청에 전역 설정으로 적용하지 않는다.
- `placeholderData(previousData, previousQuery)`에서 현재 사용자·워크스페이스·프로젝트 식별자가 이전 query key와 일치하는 경우에만 이전 데이터를 반환한다. 사용자 구분이 없는 목록 key는 세션 사용자 식별자를 포함하도록 필요한 범위를 검토한다.
- 워크스페이스·프로젝트·사용자 전환에서는 이전 범위 데이터를 표시하지 않는다. 상세 문서 및 화이트보드 편집기에는 이전 문서 유지 옵션을 적용하지 않는다.
- 401/403 및 접근 상실, 404와 재시도 UI는 기존 계약을 보존하고 지연하지 않는다. 새 검색 실패를 이전 검색의 성공으로 오인하지 않도록 오류 상태를 우선 처리한다.
- 서버 API·DB·권한 정책 변경은 없다. mutation 버튼 로딩은 이번 조회 로딩 지연과 구분한다.

## 변경 범위

- 공통 `shared/ui/loading-state.tsx`: 지연 표시와 중앙 정렬 상태. 기존 `spinner.tsx` 재사용.
- 프로젝트·화이트보드 문서·멤버의 목록 UI 및 query hooks.
- `AuthenticatedWorkspaceLayout`, `WorkspaceRedirectPage`, `AccountPage`, `ProjectDetailPage`, `WhiteboardEditorPage`.
- `shared/ui/sidebar.tsx`, `shared/ui/user-picker.tsx`의 조회 로딩. 기존 스켈레톤 원형은 유지.

## 접근성 및 검증

표시된 로딩은 `role="status"`와 안내 문구를 사용하고, 미표시 상태에는 불필요한 live announcement를 만들지 않는다. 결과 영역에는 필요한 `aria-busy`만 적용한다. 모션 감소 설정에서 스피너·스켈레톤 애니메이션을 줄이고 상태 의미는 유지한다.

- 가짜 타이머: 299ms 미표시, 300ms 표시, 완료 즉시 해제, 재진입 초기화, unmount 타이머 정리.
- 요청 지연 테스트: 검색·정렬·페이지 변경 동안 이전 목록 유지, 새 결과·빈 결과·오류로 교체.
- 경계 테스트: 계정·워크스페이스·프로젝트 변경 시 이전 데이터 미노출, 접근 상실 즉시 기존 오류 경로 진입.
- 편집기: 조회와 lazy 로딩의 연속 대기, 빠른 조회/느린 모듈 조합, 기존 오류·미저장 보호 회귀.
- 브라우저: 빠른 응답과 느린 네트워크, 데스크톱·모바일에서 중앙 정렬과 높이 안정성 확인.
- 프로젝트 명령으로 관련 Vitest, 전체 테스트, lint, build 실행.

## 현재 확인한 근거

프로젝트·문서 목록은 `isLoading`에 따라 텍스트를 즉시 표시한다. 멤버 목록과 사용자 선택기는 스켈레톤을 즉시 표시한다. 편집기는 데이터 pending과 Suspense fallback 양쪽에서 `p-6` 문구를 사용한다. 멤버 후보 query에는 이미 `keepPreviousData`가 있다. 관련 14개 경로의 그래프 커버리지는 기록된 누락이 없었으며 직접 소스 확인을 병행했다.

## 후속 승인: 스켈레톤 일관성

2026-09-22 사용자가 아래 제안을 승인했다. 이 절은 앞의 목록 스피너 규칙을 대체한다.

- 프로젝트·화이트보드 최초 목록은 현재 카드/테이블 보기와 같은 구조의 스켈레톤으로 표시한다. 카드에는 각 리소스의 미리보기·제목·메타데이터·작성자 영역을 반영한다. 테이블은 기존 열 너비·헤더·행 높이를 따른다.
- 프로젝트 상세는 헤더만 표시하지 않고 헤더·검색 도구·문서 목록 영역을 처음부터 확보한다. 조회 단계가 바뀌어도 동일 영역의 스켈레톤이 이어지도록 최초 로딩 시작 시점을 공유한다.
- 워크스페이스 셸은 기존 사이드바와 본문 구조를 유지하고, 확정되지 않은 영역은 스켈레톤으로 표시한다. 사이드바 워크스페이스 이름과 계정의 참여 워크스페이스도 해당 영역 형태를 따른다.
- 이미 정렬된 멤버 목록·추가 모달의 행 스켈레톤은 재사용한다. 편집기는 기존 스피너를 유지한다.
- 300ms 지연, 검색 중 이전 결과·빈 상태 유지, 오류·권한 즉시 처리 계약은 유지한다. API와 권한 확인 순서는 변경하지 않는다.
- 검증은 카드/테이블 전환, 최초 299/300ms, 상세 헤더→목록 연속 대기, 셸 레이아웃과 모바일 가로 넘침을 포함한다.
